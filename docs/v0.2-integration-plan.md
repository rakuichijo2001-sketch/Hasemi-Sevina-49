# Hasemi-Sevina-49 v0.2 TinyQV integration plan

Status: approved proof-of-integration plan (implementation branch only)  
Branch: `design/hasemi-v0.2-tinyqv`  
Golden parent: `44ae9879e6f25999b8569dbe8b5acdf4e2fd1a9a`  
Target: Tiny Tapeout SKY26d, SKY130A, 3x2 tiles, 10 MHz

## 1. Fixed architectural boundary

Hasemi v0.1 remains the hardware risk-processing accelerator. The existing
`hs49_register_bank`, `hs49_sensor_validator`, `hs49_risk_engine`,
`hs49_risk_fsm`, and `hs49_event_logger` functional semantics are not changed.
The v0.2 experiment adds a small RV32EC control subsystem that boots from an
external QSPI flash, uses external QSPI PSRAM for data memory, and reaches the
existing Hasemi register bank through an MMIO bridge.

The existing external SPI register interface remains available on `ui_in[2:0]`.
The SPI master and CPU share the register bank through explicit arbitration;
an active external SPI transaction has priority and stalls CPU MMIO rather than
dropping either request.

### 3.1 Files to reuse unchanged initially

The minimum dependency closure for CPU plus external QSPI memory is:

- `cpu/tinyqv.v` - CPU/memory-system wrapper and external transaction bus;
- `cpu/cpu.v` - instruction buffering and CPU control;
- `cpu/core.v` - serial RV32EC execution core;
- `cpu/decode.v` - instruction decoder;
- `cpu/alu.v` - ALU, shifter and serial multiply logic;
- `cpu/register.v` - rotating register file;
- `cpu/counter.v` - rotating counters;
- `cpu/mem_ctrl.v` - instruction/data transaction arbitration;
- `cpu/qspi_ctrl.v` - shared flash/PSRAM QSPI controller.

They are placed under `src/cpu/tinyqv/` with a local provenance file. Keeping
the imported files byte-identical in the first integration makes later diffing
against upstream unambiguous.

### 3.2 Files intentionally not imported

- the TT06 `tt_um_MichaelBell_tinyQV` top wrapper;
- GPIO mux and demo/debug signal selection;
- UART TX/RX and debug UART;
- generic SPI peripheral;
- PWM and FPGA wrappers;
- program examples, programmers and board-specific MicroPython;
- `qspi_flash.v`, which is not in the TT06 SoC source list and is superseded by
  `mem_ctrl.v` plus `qspi_ctrl.v` for this integration;
- TinyQV unit/formal test suites except for testbench ideas reused with clear
  attribution.

No crypto extension or Hasemi custom instruction is introduced.

### 3.3 Local adaptation points

Imported upstream files are not edited unless a verified tool or integration
problem requires it. Local behavior is added in separate modules:

- `hs49_mmio_bridge`: decodes Hasemi MMIO, defines byte/word behavior and
  arbitrates access to the existing byte register bank;
- top-level wiring: maps QSPI to `uio[7:0]`, ties unused TinyQV interrupts low,
  and preserves Hasemi outputs and external SPI;
- reset/output guard: forces deterministic QSPI output and output-enable values
  while reset is asserted.

## 4. CPU bus and MMIO contract

TinyQV exposes a 28-bit address plus encoded read/write sizes:

| Encoding | Transfer |
|---|---|
| `00` | 8-bit |
| `01` | 16-bit |
| `10` | 32-bit |
| `11` | no transaction |

Addresses with `addr[27:25] == 3'b000` are owned by the QSPI memory controller.
Other addresses use the external data bus. Hasemi is assigned the aligned
128-byte window `0x0800_1000` to `0x0800_107F`. The existing 7-bit register
offset is preserved exactly.

The Hasemi bank is byte-native. Only 8-bit MMIO loads/stores have register-bank
side effects in v0.2. A 16/32-bit access to the Hasemi window completes
deterministically, returns `0xFFFF_FFFF` for reads, and performs no write. An
unmapped external access also completes and returns `0xFFFF_FFFF`. This avoids a
CPU deadlock while making unsupported access visible to firmware.

## 5. QSPI memory architecture

The verified TT06 mapping is retained:

- `0x0000_0000`-`0x00FF_FFFF`: flash, execute/read only;
- `0x0100_0000`-`0x017F_FFFF`: PSRAM A, read/write;
- `0x0180_0000`-`0x01FF_FFFF`: PSRAM B, read/write (optional/reserved in v0.2).

Instruction fetches and memory data share one QSPI bus and are serialized by
the imported memory controller. The design contains no synthesized program RAM
or bulk data RAM.

## 6. Clock and reset strategy

- one Tiny Tapeout `clk` domain at 10 MHz;
- no PLL, generated core clock, false path or multicycle exception;
- the upstream CPU wrapper's one-cycle synchronous reset staging is retained
  initially because it is part of the tested core integration;
- memory controller and QSPI state use the top-level synchronous active-low
  reset input;
- `uio_oe` is forced to zero during reset;
- chip selects are driven inactive and QSPI clock/data outputs are deterministic
  during reset, even though the pads are inputs at that time.

TinyQV samples the flash/PSRAM latency code from QSPI data inputs during reset.
External hardware must prepare flash continuous-read mode and PSRAM QPI mode
before releasing reset, as in the upstream boot contract.

## 8. Technical risks

| Risk | Initial control/evidence required |
|---|---|
| CPU plus accelerator exceeds 3x2 area | synthesis and real 3x2 hardening; no estimate-only FIT decision |
| Rotating register file becomes excessive FF/mux logic | inspect sequential/mux counts and mapped register structure |
| Shared QSPI timing or contention | check `uio_oe` by phase, reset behavior and behavioral flash/PSRAM tests |
| CPU MMIO starves/corrupts external SPI | external-SPI-priority arbiter and simultaneous-activity test |
| Unsupported MMIO size silently corrupts registers | deterministic error value and no-write tests |
| Boot depends on external mode preparation | document and model the upstream reset/latency contract |
| Upstream reset staging conflicts with TT flow | startup/mid-transaction/reset-repeat tests plus GLS |
| Core logic optimized away | verify instruction activity, MMIO side effects and synthesis hierarchy/cells |
| 10 MHz changes QSPI assumptions | test at 10 MHz; QSPI SCK is nominally 5 MHz |
| Physical flow converges only with unsafe constraints | no fake false/multicycle paths; report failure rather than waive it |

## 9. Phase exit criteria

1. Imported source compiles with the existing Hasemi RTL.
2. Directed bridge and top-level tests pass without changing v0.1 expected
   values.
3. A QSPI-flash program boots, performs Hasemi reads/writes and exercises PSRAM.
4. Synthesis shows no inferred bulk on-chip memory, unexpected dead core, or
   untriaged critical warning.
5. 3x2 hardening, STA, DRC/LVS/antenna, precheck and GLS evidence determine the
   final FIT/FIT WITH REDUCTION/DOES NOT FIT decision.
